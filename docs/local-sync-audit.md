# Аудит локальной синхронизации RussTube

Дата: 31 октября 2026 г. Ветка: `feature/local-sync-audit`. Это этап 0 и предложение архитектуры; код синхронизации, разрешения и интерфейс сопряжения ещё не изменялись.

## 1. Карта проекта

| Область | Текущее состояние |
| --- | --- |
| Сборки | Один Gradle-модуль `:app`, два product flavor: `mobile` и `tv`. Общий Java-код находится в `app/src/main/java`, различаются ресурсы и manifest-надстройки в `app/src/mobile` и `app/src/tv`. Отдельной общей библиотеки нет. |
| Идентификаторы | TV: `ru.russtube.tv`; Mobile: `ru.russtube.tv.mobile`. Это разные песочницы Android, поэтому прямое чтение данных другого приложения исключено. Менять applicationId не требуется. |
| Инструменты | Android Gradle Plugin 9.3.1, Java 17; Kotlin-плагина и Kotlin-кода нет. `minSdk 23`, `targetSdk 35`, `compileSdk 36`; Media3/ExoPlayer 1.10.1, OkHttp 4.12.0. |
| Экран каталога | `BrowseActivity` (TV), `MobileBrowseActivity` (Mobile), `FeedRepository` и адаптеры RUTUBE/VK/OK/Дзен/PeerTube. TV-настройки — `TvSettingsActivity`; мобильные — `MobileSettingsPanel`. |
| Плеер | `PlayerActivity` (TV) и `MobilePlayerActivity` используют `PlaybackEngineFactory` и Media3. `StreamResolver` получает свежие потоки площадок; `AudioPlaybackService` обслуживает фоновое воспроизведение на телефоне. Команды сейчас привязаны к private-методам Activity, отдельного удалённого интерфейса нет. |
| Сеть | `NetworkProxy` настраивает HTTP/SOCKS5 для площадок и медиасегментов. NSD, локального сервера, WebSocket, доверенных устройств и обмена данными пока нет. LAN-транспорт нужно отделить от прокси видеоплощадок. |

## 2. Существующие модели и хранилища

Все перечисленные ниже пользовательские данные лежат в приватных `SharedPreferences`; Room, SQLite и DataStore пока не применяются.

| Модель / файл | Хранение и ключ | Ограничение для синхронизации |
| --- | --- | --- |
| `VideoItem`, `VideoJson` | Метаданные видео: площадка, заголовок, thumbnail, `playUrl`, `pageUrl`, длительность, канал, `isLive`, просмотры и дата. `stableKey()` использует площадку и URL страницы, при его отсутствии — `playUrl`. | URL и иногда ключ доступа VK не являются стабильной или безопасной общей идентичностью. Поля нужно фильтровать перед отправкой. |
| `FavoriteStore` | `favorites/videos`, JSON-массив до 1000 элементов; `set` удаляет совпадение и добавляет в начало. | Нет версии записи, tombstone и журнала удаления. |
| `SubscriptionStore` | `subscriptions/channels`, JSON-массив до 100 каналов; уникальность — площадка и `channelId`. | Нет журнала операций; сохранённый `VideoItem` может содержать лишние URL. |
| `WatchHistoryStore` | `watch_history`: `order` и отдельные `video_<hash>`; до 1000 записей, метка `lastWatchedAt`. Есть миграция старого состояния плеера и очистка истории с порога времени. | Удаление также удаляет позицию, но не оставляет tombstone. История появляется после порога просмотра; очистку нужно распространять как операции. |
| `WatchProgressStore` | `watch_progress`: SHA-256 от `source|pageUrl` (первые 16 байт), позиция, длительность, `order`, локальный флаг зеркалирования. Новая запись обычно появляется после 10% просмотра; неизвестная длительность — после 60 секунд. | Нет сеанса, признака завершения и явного перезапуска; позицию нельзя сливать правилом «максимум». `mirrored` — локальная настройка устройства, синхронизировать её не надо. |
| `StateStore` | `playback_state`: последний экран/запрос, текущее видео, позиция, скорость и режимы плеера. | Это локальное состояние навигации, не библиотека пользователя. В обмен можно выделить лишь согласованные настройки плеера. |
| `SavedFilmsStore` | `saved_films/videos`, до 1000 вручную добавленных видео. | Это отдельная подборка фильмов, не система именованных пользовательских плейлистов. |
| `TvChannelStore` | `tv_channel_catalog`: локальный каталог эфиров, порядок, избранное, скрытие, статус, импорт/экспорт. | Не включать в первую волну синхронизации без отдельной схемы: его `favorite` означает избранный телеканал, а не `FavoriteStore`. |
| `MobileLibraryTransfer` | JSON v1 для экспорта/импорта подписок и избранного между Mobile и TV. | Импорт пишет `SharedPreferences` напрямую и не создаёт события изменений; при появлении журнала этот путь необходимо провести через общий шлюз записи. |
| Настройки | `mobile_browse`, `browse`, `tv_player`, `tv_scale`, `tv_appearance`, `network_proxy`, `caption_preferences` и другие preference-файлы. | Масштаб/темы/прокси должны остаться локальными; скорость и параметры субтитров синхронизировать лишь по явному выбору. |

Поиск сохраняет последний запрос через `StateStore`, но отдельной истории поисковых запросов нет. Пользовательских именованных плейлистов также нет: упоминания `playlist` в PeerTube относятся к HLS/видеопотокам. Shorts в текущем мобильном меню отсутствует. Следовательно, критерий синхронизации плейлистов потребует сначала ввести минимальную локальную модель плейлистов в обеих версиях; нельзя выдавать `SavedFilmsStore` за готовые плейлисты.

История и позиции меняются из обоих плееров и фонового аудиосервиса. Подписки/избранное меняются из каталогов, плееров и контекстных действий. Все эти пути, а также импорт и массовую очистку истории, нужно провести через один слой операций, иначе локальные изменения будут пропущены.

## 3. Идентификация контента и ограничения

Предлагаемый ключ — `(platform, contentType, contentId)`; `contentType` различает `VOD`, `LIVE` и `LIVE_RECORD`. Нормализатор должен быть отдельным протестированным компонентом и отклонять неоднозначные ссылки:

- RUTUBE: стабильный 32-символьный ID видео из каталога/страницы. Live-ссылка и запись не объединяются автоматически.
- VK Видео: `owner_id` + `video_id`; суффикс `access_key` не входит в ключ и не передаётся на другое устройство. Если доступ без ключа невозможен, телевизор сообщает об этом, а не получает секрет с телефона.
- OK.ru: числовой ID `/video/<id>`.
- Дзен: ID `/video/watch/<id>`.
- PeerTube: нормализованный HTTPS origin экземпляра + UUID/короткий ID видео; один UUID на разных серверах не должен склеиваться.

`VideoItem.isLive` отражает состояние выдачи в момент получения. Преобразование live в запись надо подтвердить метаданными платформы, а не делать по одному URL. Для элемента без проверяемого ID — локальная запись без автоматического обмена до нормализации. Подписки используют отдельный ключ канала `(platform, instance?, channelId)`.

Протокол не переносит `playUrl`, `.m3u8`, `.mpd`, cookies, подписанные адреса обложек, ключи доступа или настройки прокси. Команда «Смотреть на ТВ» содержит нормализованный ID и безопасные метаданные; TV самостоятельно вызывает существующий `StreamResolver`. Если источник нельзя открыть анонимно, показывается ошибка.

## 4. Предлагаемая архитектура (на согласование)

1. **Равноправные узлы.** Каждый экземпляр Mobile/TV имеет UUID устройства, локальную идентичность и собственный журнал. При включённой функции и активном приложении он объявляет `_russtube._tcp` через Android NSD с назначенным системой портом. TXT-записи: версия протокола, тип устройства и возможности без секретов. NSD применяется для поиска; ручной IP/порт — резерв, если mDNS не проходит между сегментами сети. `ConnectivityManager.NetworkCallback` отслеживает смену Wi-Fi/Ethernet и обновляет регистрацию/соединение; IPv4 и IPv6 проверяются отдельно. Одинаковый IP для устройств не требуется, маршрутизация между ними требуется. Перед публичным выпуском следует проверить регистрацию выбранного типа сервиса в IANA.
2. **Защищённый канал.** Предлагается TLS поверх `SSLSocket` с ограниченными по длине бинарно-окаймлёнными JSON-сообщениями. Это осознанный выбор вместо WebSocket: в проекте есть OkHttp-клиент, но нет проверенного WebSocket-сервера; самодельный сервер добавит риск, а тяжёлая зависимость не нужна. Если совместимость именно с WebSocket важна, выбрать проверенную серверную библиотеку до этапа 1. LAN-сокеты не проходят через `NetworkProxy`.
3. **Идентичность и сопряжение.** Подписывающий EC-ключ создаётся в Android Keystore, приватная часть не экспортируется. На TV одноразовая QR-сессия (например, 2 минуты) содержит адрес/порт, nonce и отпечаток публичной TLS-идентичности, но не секрет. Телефон проверяет отпечаток; TV показывает имя/тип телефона и запрашивает подтверждение. При ручном вводе адреса оба экрана показывают одинаковый короткий код сверки из аутентифицированного transcript: пользователь сравнивает его, прежде чем доверить ключ. Обе стороны сохраняют только доверенные публичные идентичности и права; отзыв немедленно закрывает сессии. Потеря ключа требует повторного сопряжения.
4. **Сеансы и протокол.** `protocolVersion`, `messageId`, `deviceId`, `type`, `payload`, номер последовательности и nonce сеанса. `HELLO/AUTH`, `CAPABILITIES`, запрос/пачка/ACK изменений, команды/состояние, `ERROR`, `PING/PONG`. Ограничения размера, частоты, глубины JSON, числа соединений и времени ожидания; проверка поддержки команды и полномочий перед исполнением. Повторный `messageId` не исполняется снова; счётчик и nonce предотвращают повтор команд из старого сеанса.
5. **Долговечный журнал.** Добавить небольшой `SQLiteOpenHelper` без Room-зависимости: `devices`, `operations`, `peer_ack`, `entity_state`, `play_sessions`, `schema_meta`. У каждого изменения UUID, origin device, локальный счётчик, версия схемы, causal context и полезная нагрузка. Журнал остаётся при выключенной сетевой функции; выключение прекращает прослушивание/обнаружение, но не уничтожает изменения. Передача пакетами с ACK, повтором после разрыва и дедупликацией по origin + operation ID. Промежуточный доверенный узел пересылает исходную операцию без замены origin и не исполняет её повторно.
6. **Мост к существующим данным.** `FavoriteStore`, `SubscriptionStore`, `WatchHistoryStore`, `WatchProgressStore` и `MobileLibraryTransfer` сохраняют публичные методы и UI-поведение. Их мутации идут через `SyncMutationGateway`: сначала долговечная операция/состояние в SQLite, затем проекция в текущие preferences; незавершённая проекция восстанавливается при запуске. Это позволяет не переписывать каталог и плеер целиком. Импорт старых preferences — однократный, с маркером схемы и проверкой количества записей до/после.
7. **Управление TV.** Внутренний `TvPlaybackController` связывает валидированные команды с текущим `PlayerActivity`/Media3 через главный поток и выдаёт снимок состояния/возможностей. Не экспортировать Activity/Service/Receiver наружу. D-pad/OK/Back направлять только в активный интерфейс RussTubeTV. `OPEN_VIDEO` запускает существующий путь разрешения потока; телефон прекращает локальное воспроизведение лишь после подтверждения запуска на TV. Состояние отсылать при изменении и с редким heartbeat, позицию на телефоне интерполировать локально.
8. **Жизненный цикл.** Discovery/сервер — при открытом приложении и включённой синхронизации; сокет и multicast освобождаются при уходе в фон. Отложенные операции передаются при следующем появлении устройств. Постоянная доступность TV через `connectedDevice` foreground service — отдельное решение после измерений и проверки требований Android, не включать постоянно по умолчанию.

### Правила слияния

- Избранное, подписки и элементы плейлистов: remove-wins observed-remove set с причинным контекстом. Tombstone подавляет старое или одновременное добавление; повторное добавление возможно только явным действием после получения удаления. Порядок и название плейлиста — отдельные детерминированные регистры с логическим счётчиком и ID устройства как tie-breaker.
- История: журнал событий просмотра с уникальным ID и меткой времени; на экране — последнее известное событие. Очистка истории создаёт операции удаления с причинным контекстом, включая массовые диапазоны; старая копия не восстанавливает удалённые записи. Новые просмотры после подтверждённой очистки создают новые события.
- Позиции: сохранять сеанс, `position`, `duration`, признак завершения и явный «начать сначала». Причинно более позднее решение побеждает. Одновременные независимые сеансы не сводить к максимальной позиции: хранить оба и при продолжении предложить выбор, затем записать выбор как новое событие. Live-позицию не переносить как VOD.
- Сборка мусора: tombstone/операцию удалять лишь после ACK всех известных доверенных узлов. Удаление давно недоступного устройства требует явного «забыть устройство» и последующей согласованной полной сверки; простое истечение срока не должно воскрешать данные.

## 5. Миграция, изменяемые файлы и риски

**Этап 1 — транспорт:** новые `LocalDiscovery`, `LocalTlsTransport`, `PairingManager`, `TrustedDeviceStore`, `LocalProtocol` в общем Java-пакете; изменения `AndroidManifest.xml`, `TubeApplication`, TV/Mobile settings. NSD на старых API — legacy callback, на новых — системный picker там, где он может заменить широкое разрешение. QR-сканер должен работать без Play Services (оценить небольшую локальную библиотеку и разрешение камеры лишь при сканировании).

**Этап 2 — данные:** новые `SyncDatabase`, `SyncMutationGateway`, `VideoIdentity`, `ConflictResolver`, `SyncEngine`, модель пользовательского плейлиста. Точечные изменения `FavoriteStore`, `SubscriptionStore`, `WatchHistoryStore`, `WatchProgressStore`, `MobileLibraryTransfer`, `SavedFilmsStore` только при согласованном включении вручную добавленных фильмов в плейлисты. Старые preferences сохранять до успешной миграции; миграцию повторять идемпотентно после сбоя. Не повышать `minSdk`/`targetSdk` ради функции.

**Этап 3 — управление:** внутренний контроллер, адаптер к `PlayerActivity`/`PlaybackEngineFactory`, `StreamResolver`, мобильные действия в `MobileBrowseActivity` и `MobilePlayerActivity`. Тестировать все поддерживаемые площадки и отказ при недоступном потоке.

**Этап 4 — UI:** категория «Синхронизация» в `TvSettingsActivity`, мобильные настройки/раздел «Устройства», список пар, QR/ручной ввод, пульт, журнал и кнопка экспорта диагностики. Настройки масштаба и темы остаются раздельными.

**Основные риски:** разные ID одного видео в выдачах; VK access key; быстрые URL обложек/потоков; отсутствие плейлистов и признака завершения; несогласованная запись в preferences и SQLite при сбое; прямой импорт, обходящий мутатор; mDNS между VLAN и на старых Wi-Fi; ограничения фонового режима; смена идентичности после переустановки; одновременное управление TV двумя телефонами. Для управления двумя контроллерами TV сериализует команды и возвращает применённое состояние/ошибку каждому; приоритет не основывается на порядке прихода сетевых пакетов без ACK.

## 6. Android и план проверки

Сейчас `targetSdk 35` и `compileSdk 36`. При переходе на target 37 Android 17 ограничивает доступ к LAN и обычно требует `ACCESS_LOCAL_NETWORK`; для выбранного NSD-сервиса системный picker может дать доступ без широкого разрешения. Для постоянно слушающего/объявляющего узла и ручного IP путь разрешений нужно отдельно проверить на API 37. Старый `NsdManager` доступен с API 16; на старых Wi-Fi может потребоваться кратковременный `WifiManager.MulticastLock`. На API 37 нельзя просто предположить, что picker покрывает серверное прослушивание. Обновление compileSdk для API 37, если понадобится, отдельно от изменения target/minSdk. [Android NSD](https://developer.android.com/reference/android/net/nsd/NsdManager), [ограничения локальной сети](https://developer.android.com/privacy-and-security/local-network-permission), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [типы foreground service](https://developer.android.com/develop/background-work/services/fgs/service-types).

После каждого этапа: unit-тесты и debug-сборки Mobile/TV. Для синхронизации дополнительно: таблица нормализации ID по источникам; миграция старых данных и повтор после прерывания; симуляция трёх узлов, разного порядка доставки, повторов и одновременных удалений; проверка границ сообщений/доступа без пары/отзыва доверия; восстановление после потери сети и смены IP. На устройствах: Wi-Fi↔Ethernet, роутер без multicast, ручной IP, Android 23/35/37 по доступности, TV-пульт и мобильный экран. Отдельно измерить расход батареи и память. Эмуляторы не заменяют проверку реальной домашней сети и поведения ТВ-приставок.

## 7. Контрольная точка

Для основной реализации требуется согласовать два решения:

1. **Транспорт:** платформенный TLS с ограниченными JSON-кадрами вместо WebSocket, чтобы не добавлять непроверенный WebSocket-сервер; NSD и пользовательское сопряжение остаются как в ТЗ.
2. **Плейлисты:** добавить полноценные именованные локальные плейлисты в обе версии на этапе 2; существующий раздел «Фильмы» оставить отдельным.

До согласования этих решений этапы 1–5 не начинаются. На этапе 0 сборки и сетевые испытания не проводились: прикладной код не менялся.
